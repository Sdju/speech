## Аннотация (CFP)

После волны хайпа на микрофронтенды стал замечать, что их берут чуть ли не в любом случае, часто считая, что это делает приложение масштабируемым, команды независимыми и так далее. Не будем отрицать возможностей, которые привносят микрофронтенды, но многие из них достижимы без необходимости перехода на данную архитектуру.

Мы с вами попробуем разобраться, когда микрофронты помогут вашему приложению, а когда усложнят его без особой на то необходимости.

## Аудитория

- Frontend / full-stack middle–senior на HolyJS
- Знают SPA, монорепы, CI/CD на базовом уровне
- Часть уже «внедрила» MFE или стоит перед решением
- Module Federation — эталонный/самый распространённый способ реализации MFE в докладе; остальные реализации не разбираем глубоко

## Проблема, которую решает доклад

MFE часто воспринимают как единственный способ получить независимость команд, масштабирование поставки, изоляцию доменов. Инженеры не видят палитры альтернатив, путают бизнесовое восприятие с технической физикой (в т.ч. через аналогию с микросервисами) и закрывают **бизнесовую** боль **техническим** распилом — хотя есть более простые пути.

Дополнительно: даже пройдя «правильную» лестницу разделений, редко спрашивают, должны ли независимые части **оставаться одним frontend**.

## Миссия

Расширить кругозор: как рационально вырастают к MFE; какие ступени static дают близкие плюсы; когда dynamic оправдан; и спросить не только «как делить», но и «зачем держать одним проектом».

## Жанр доклада

**Архитектурный**, не DevOps-туториал. Сквозной вымышленный продукт **«Ябе.ру»** — носитель лестницы (не кейс SM Lab).

- Мало кода на сцене — только там, где нужна фактура «что происходит».
- Без привязки к конкретному стеку (React/Vue/…); идеи переносимы.
- Не привязываемся к кейсам SM Lab — обобщённый суперприложение-паттерн.
- Эталон реализации MFE в примерах: **Module Federation**.
- Реализации MFE в индустрии очень разные — все не разбираем; в докладе фиксируем рабочую границу.
- Каламбуры бренда — редкий ритм (см. `narrative.md`), не стендап.

## Носитель повествования · Ябе.ру

Вымышленный рост: Такси → Go → Еда → Pay → Travel.

Каждый продуктовый шаг = следующий архитектурный:

| Продукт | Архитектура |
|---------|-------------|
| Ябе.ру (такси) | flat |
| + Go | modules |
| + Еда | monorepo |
| + Pay | npm-пакеты |
| + Travel | MFE (shell + remotes) |

Финальный поворот: при полной независимости команд/деплоев — **почему это всё ещё один frontend?**

Детали, каламбуры, UI-гэг: `collected/narrative.md`.

## Рабочее определение MFE в докладе

**Микрофронтенды** здесь — архитектуры с **динамической линковкой** (runtime composition; эталон — Module Federation).

Альтернативы на пути к независимости — из мира **статической линковки** (модульность → монорепа → NPM/пакеты): близкие плюсы, другая физика цены.

Жёсткий контракт «MFE = dynamic» удобно зафиксировать при прибытии на этап Travel / сразу после поворота — не обязательно в первых минутах.

## Центральная рамка выбора

1. Боль и решение смотрим в плоскостях **бизнес** и **техника**.
2. Сначала: в какой плоскости боль (или в обеих)?
3. Потом инструмент — **не закрывая чисто бизнесовую задачу сугубо техникой**, если есть проще.
4. После распила: **должны ли части оставаться одним frontend / одним продуктом?**

## Опорный тезис: MFE ≠ микросервисы

Идёт **после** рамки бизнес/техника и (в новой драматургии) **после** эмоционального прибытия на MFE через Ябе: на контрасте видно, что **бизнесовое восприятие** («как микросервисы») **не совпадает с технической физикой**.

| | Микросервисы | Микрофронтенды (эталон — MF, dynamic) |
|--|--------------|----------------------------------------|
| **Масштабирование** | Независимое, в т.ч. горизонтальное | Единый DOM / одна сессия; горизонтально «домасштабировать кусок UI» нельзя |
| **Эволюция** | Постепенно через версии API | Единый визуальный гайдлайн; две версии кнопки/DS пользователю не показать |
| **Задачи** | Свой класс техзадач бэка | Другой класс задач UI/команд/деплоя фронта |

## Главный takeaway

Сначала понимаем, чего хотят от независимости. Рациональный рост (Ябе) показывает: много плюсов достижимо **static**-ступенями; MFE — прыжок в **dynamic**. Бизнес-восприятие часто расходится с техникой (MS ≠ MFE). Выбор — с плоскости боли. И отдельно: умение добавлять части в систему ≠ ответ, **нужно ли** их туда добавлять / держать одним frontend.

## Обещание доклада

1. Общий язык: что обещают MFE / независимость команд и поставки.
2. Рамка «бизнес / техника».
3. Сквозная история Ябе: flat → modules → monorepo → packages → MFE.
4. Поворот: «почему один frontend?» + ось static vs dynamic + цена dynamic.
5. Когда остановиться раньше / когда dynamic ок · артефакт · итог.

## Палитра ступеней · мир static → dynamic

| # | Ступень (Ябе) | Что даёт | Чего не даёт / цена |
|---|---------------|----------|---------------------|
| 0 | Flat (такси) | Скорость старта | Границы при росте доменов |
| 1 | **Модульная** (Go) | Ownership, простота | Независимые пайплайны |
| 2 | **Монорепозиторий** (Еда) | Явные границы; деплой простой | Пайплайны по поддеревьям возможны; цена tooling |
| 3 | **Статическая линковка** (Pay) | Независимость артефактов, ошибки до runtime | Версии, контракты; общий финальный deploy продукта |
| 4 | **MFE / MF** (Travel) | Независимый deploy кусков UI | Runtime-стыки, shared deps, UX/контракты; всё ещё «один» продукт для пользователя |

## Артефакт

- Live-демо на сцене: `defer`.
- **Да:** внутри доклада, путь `example/<example-name>/` (не отдельный репозиторий): проект × несколькими путями + cookbook.
- Кандидат имени: `yabe` / `yabe-ru` (ещё не зафиксировано).
- На сцене — выводы и указатель; глубина — в `example/…`.

## Тон

Инженерно-архитектурный, спокойный, с редким brand-play. Расширяем кругозор, не хороним MFE. Каждый шаг Ябе — рационален.

## Ограничения

- Не гайд по настройке MF / CI / k8s
- Не кейсы SM Lab
- Мало кода, без привязки к стеку
- Не deep-dive всех MFE-фреймворков — эталон MF
- Не стендап: каламбуры только по ритму из `narrative.md`
- Не объяснять UI-гэг до финала (опционально один раз в повороте)
