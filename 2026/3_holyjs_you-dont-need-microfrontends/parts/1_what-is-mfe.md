<!--
Тезисы по кликам (раньше были подписью на слайде, с номером претензии из 7):
0 — 1/7 Разделение: где провести границы?

Семь претензий на той же схеме. Dev и массовая миграция раскрываются в два состояния.
Старт: границы Catalog и Cart. Кому принадлежат промокоды и расчёт скидки?
Это пример неоднозначного разделения ответственности, а не рекомендация границ.
Клик 1: CI/CD. У каждого свой pipeline, публикация и откат, но совместимость
частей всё равно нужно проверять вместе. Общий прогон показан как пример такой проверки.
Клик 2: Dev — весь продукт локально: shell, все remotes, API, конфиги и версии.
Клик 3: альтернатива — один Catalog; тестовая оболочка, моки API и соседей.
Изоляция требует работы и проверки того, что тестовые замены соответствуют реальности.
Клик 4: хрупкая интеграция. Cart проходит свой CI, публикует v2 и ломает
взаимодействие с Catalog v1. Независимый деплой не гарантирует совместимость.
Клик 5: раскрываем несовпадение: Catalog отправляет id, а Cart уже ожидает productId.
Здесь пояснить, почему TS и договорённости о версиях сложнее поддерживать между
независимо собираемыми и выпускаемыми частями.
Клик 6: единый стиль — общая UI library, одинаковые кнопки, компоненты и токены.
Клик 7: массовая миграция API этой библиотеки с v1 на v2 затрагивает всех потребителей.
Клик 8: Catalog переведён на v2; Shell, Cart и Profile ещё предстоит перевести.
Это статус изменения исходников потребителей, не автоматическая подмена singleton в рантайме.
