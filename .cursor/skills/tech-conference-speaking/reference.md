# Reference

## Когда какая фаза нужна

### Фаза 1: сбор фактуры
Используй, когда:
- темы доклада ещё нет в ясном виде;
- есть только идея, CFP, заметки или набор тезисов;
- нужно понять аудиторию и обещание доклада;
- есть риск сделать красивые, но пустые слайды.

Не пытайся здесь:
- писать полный `slides.md`;
- детализировать каждый пример;
- выбирать точные анимации и компоненты.

### Фаза 2: wireframe
Используй, когда:
- уже понятны цель и примерный план;
- нужно проверить драматургию до написания содержимого;
- надо понять количество и назначение слайдов.

Wireframe должен отвечать на вопросы:
- зачем существует этот слайд;
- что слушатель должен понять после него;
- нужен ли тут клик, схема, код или пауза.

### Фаза 2.1: стилистика и дизайн
Используй, когда:
- narrative уже более-менее держится;
- хочется выбрать визуальное направление до реализации;
- нужно согласовать тон: академичный, дерзкий, инженерный, playful и т.д.

Дизайн-решения описывай как систему:
- основные фоны;
- принцип для кодовых слайдов;
- принцип для схем;
- принцип для "переходных" и "панчлайн" слайдов.

### Фаза 3: markdown-презентация
Используй, когда:
- логика уже устоялась;
- пора писать контент;
- визуальные решения ещё можно откладывать.

Приоритет:
1. Техническая точность.
2. Понятность переходов.
3. Темп чтения/объяснения.
4. Только потом декоративность.

### Фаза 4: материализация
Используй, когда:
- содержание уже не разваливается;
- есть понимание, что показывать;
- пора вкладываться в визуал и интерактив.

Материализация не должна:
- лечить плохую структуру;
- маскировать слабый тезис;
- добавлять клик-флоу ради самого клик-флоу.

## Как оценивать темп

Приблизительно считай тайминг по смысловым блокам, а не по числу слайдов.

Смотри на:
- количество новых терминов подряд;
- объём кода, который нужно проговорить;
- плотность визуальных изменений;
- число "ментальных переключений" между соседними слайдами.

Сигналы перегруза:
- 3+ новых идеи подряд без промежуточного вывода;
- длинные кодовые морфы без verbal checkpoint;
- важная оговорка появляется позже, чем сильное утверждение;
- слайд показывает больше, чем спикер успевает обосновать.

## Что хранить в `collected/`

Минимальный набор:

```text
collected/
  brief.md
  plan.md
  questions.md
  design.md
```

Расширенный набор:

```text
collected/
  brief.md
  audience.md
  plan.md
  timings.md
  questions.md
  design.md
  references.md
  fact-check.md
```

## Как работать с неизвестностью

На ранних этапах помечай каждый спорный кусок как одно из:
- `fact` — уже подтверждено;
- `hypothesis` — правдоподобно, но требует проверки;
- `unknown` — пока нет ответа;
- `defer` — сознательно отложено до следующей фазы.

Это помогает не переусердствовать в фазе 1 и не притворяться, что всё уже ясно.

## Послайдовый статус

В комментарии wireframe/реализованного слайда:

| `Статус` | Значение |
|----------|----------|
| отсутствует / `wireframe` | заглушка `<СЛАЙД · …>`; не материализовать |
| `реализация` | можно заменить заглушку на контент (md → визуал) |

Комментарий остаётся source of truth. Если пользователь изменил `Контент`/`Спикер` или видимый текст — агент синхронизирует материализованное тело, не откатывает правку.

## Как переходить между фазами

Перед переходом фиксируй короткий checkpoint:

```markdown
## Phase checkpoint

Текущая фаза: <название>

Готово:
- ...

Открыто:
- ...

Переход возможен, потому что:
- ...

Нужно проверить дальше:
- ...
```

## Когда подключать рендер/CDP

Проверяй реальный рендер, если:
- смысл зависит от порядка появления элементов;
- есть сложный `timeline` или многошаговый `magic-move`;
- есть риск, что визуал спорит с речью;
- неочевидно, что именно увидит зритель на конкретном клике.

Если рендер не доступен, зафиксируй это как технический риск, а не замалчивай.
